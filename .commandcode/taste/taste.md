# Workflow
- User prefers commands to run without per-command approval prompts (attempted `cmd --yolo` to enable auto-approval instead of approving each command individually; when handed copy-pasteable commands due to blocked permissions, replied "run the commands" and restored auto-approval so the assistant could execute them itself). Confidence: 0.6
- When the assistant's shell access is blocked by permission mode, user wants the assistant to stop trying to run commands and instead hand off exact, copy-pasteable commands for the user to run themselves ("Ask me for the commands"), offering fallback variants for shell compatibility and asking whether to restore auto-approval. Confidence: 0.6
- When an app operation needs doing (group, scan, analyze, export), user prefers the assistant to trigger it directly (e.g., hit the API endpoint / run the command) rather than give click-by-click UI instructions — e.g., replying "I want \"Kreta\" grouped" right after being offered either path. Confidence: 0.6
- User reports UI bugs as terse symptom descriptions often paired with an observed workaround (e.g., "Sometimes the review interface hangs for keyboard input, using a mouse to click helps"), leaving root-cause diagnosis and the fix to the assistant rather than suggesting the technical cause. Confidence: 0.55
- User requests new features as terse numbered lists of concrete requirements (e.g., "1) Start tournament with pairs of similar photos 2) Before the export, let me select photos to skip."), leaving implementation details, sequencing, and design choices entirely to the assistant. Confidence: 0.5

# Product / App Design
See [product-/-app-design/taste.md](product-/-app-design/taste.md)

- User expects production data migrations to handle upgrading an existing deployed database, not just fresh setups — the assistant should add regression tests that reproduce the deployed scenario (old schema/DB) before pushing a fix. E.g., when a THUMB_SIZE bump left stale sha1s in the production DB, a regression test simulating a stale sha1 on an unchanged photo was added before the fix was pushed. Confidence: 0.7

- User expects UI status indicators and progress displays to reflect the actual backend state, not hardcoded/mock values — a scan button stuck on "Scanning..." after the job completed, and tournament progress stuck on "0/4 views" (hardcoded `max_views` instead of real votes_done/total_votes) are both UI defects; running state/progress should derive from real server state (SSE/API), not client-side flags set on click or frontend constants that are never updated. Confidence: 0.75
- For photo-sorter grouping, user wants exactly two group types: (1) "series" groups of up to 16 photos taken around the same time with similar objects/framing — so he can pick the best one from a burst/series; (2) non-series singles batched into groups of 4 (chronologically, for review context). He explicitly rejected the previous grouping ("I am not happy with the groupings") and stated this split as the desired algorithm. Confidence: 0.9
- When the current implementation is buggy or produces unsatisfactory results (e.g., the greedy photo-grouping algorithm that hung and grouped poorly), user prefers the assistant to compare against previous attempts in sibling project directories (../photo-sorter) and port the working algorithm/approach rather than keep patching the current code — explicitly suggested "Maybe you should also port the old one." Confidence: 0.7
- User relies on keyboard input for the review and tournament interfaces (arrow keys, Enter, Tab, Space, Backspace) and treats dropped/hung keystrokes as a blocking UX defect — reported "Sometimes the review interface hangs for keyboard input, using a mouse to click helps." Keyboard event handling must be stable (one-time listener calling the latest handler via a ref) so keystrokes are never lost during state changes/re-renders; the same defect on the Tournament page was expected to get the same fix. Confidence: 0.65
- For the photo-sorter rankings feature, user expects the ranking to contain only photos he actually rated (rating > 0 / tournament participants), not every catalog photo — unrated photos with default ELO 1500 dominating the ranking (777 photos) was reported as a defect ("The rankings is full of photos I didn't star rate... They dominate the ranking"); rankings should reflect the user's judgments, not the whole library. Confidence: 0.75
- For the photo-sorter tournament, user wants similar/burst photos from the same review group paired against each other first, before competing against photos from different scenes — so duplicates are eliminated mechanically rather than both surviving. He noticed his own bias let near-identical photos both reach the top of the rankings ("even with initial grouping they survived, and because I am biased both of them ended with high rankings") and explicitly requested "Start tournament with pairs of similar photos." Confidence: 0.8
- Before exporting the final selection, user wants to manually curate the set: a per-photo skip control on the rankings grid (persisted in the DB, toggleable, and excluded from both the export preview count and the actual export copy) — explicitly requested "Before the export, let me select photos to skip." Confidence: 0.8
